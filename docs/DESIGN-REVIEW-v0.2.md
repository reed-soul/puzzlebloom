# 设计评估 v0.2 — 从"统一但平淡"到"一进门就想玩"

> 评估对象：PuzzleBloom v0.1（commit `ba50def`）
> 评估角度：儿童心理学（唤醒度 / 注意 / 奖励反馈）× 色彩学（OKLCH 实测）
> 结论：v0.1 的"平淡"不是审美问题，是三处可测量的结构性缺陷。本文给出实测数据、成因、以及已经落地的改法。

---

## 0. 结论先行

三句话：

1. **色彩不是"太素"，是"素在了大面积上、艳在了小面积上"。** v0.1 最饱和的颜色只出现在徽章、图标这类占屏不到 4% 的地方；98% 的像素彩度低于 OKLCH C 0.05，而儿童品牌这条线在 0.20 左右。眼睛扫过去，没有任何一块颜色值得停留。
2. **视觉层级塌了，因为没有"地平线"。** 页面底色与卡片底色的明度差只有 ΔL 0.016–0.058，卡片浮不起来；唯一的高饱和色（accent）同时兼任徽章、提示、按钮三种角色，于是哪个都不重要。
3. **交互只有"结果"，没有"奖励"。** 落子、完成一行、切换页面，三种最该被感知的时刻，v0.1 里其中两种是硬切，一种只在数字模式下有 180ms 的缩放。

处方一句话：**把一个装饰色的彩度放开、面积做大（`sky`），把最亮的颜色扶正成最大色块并给它一个深色标签（`accent` + `accentInk`），再用浏览器原生的转场/描边/补间把三个"结果时刻"变成"奖励时刻"。**

改完的实测：截图像素平均彩度 **0.0141 → 0.0376（2.7×）**，90 分位 **0.018 → 0.064**，99 分位 **0.093 → 0.160**（已进入儿童品牌区间），五个主题 × 八组对比度全部通过。

## 1. 怎么测的

不用"我觉得"，用三个可复算的量：

| 量 | 做法 | 为什么用它 |
| --- | --- | --- |
| **彩度 C** | sRGB → OKLab → OKLCH，取 `hypot(A, B)` | OKLCH 的 C 是感知等距的饱和度轴。RGB 的 saturation 在同一色相不同明度下不可比，正是它让"这个黄和那个蓝一样艳"这种判断出错 |
| **面积加权彩度** | 把整页截图降采样到 220px 宽，逐像素转 OKLCH 取均值 / 分位数 | 一个颜色再艳，占 1% 面积也不构成"有颜色"。**面积×彩度**才是观感 |
| **对比度** | WCAG 2.1 相对亮度，八组配色对 | 加饱和度的唯一合法前提，是文字还能读 |

复算入口：`packages/theme-core/tests/palette.test.ts`（42 条断言，`pnpm test` 即跑），像素测量脚本见文末。

### 儿童品牌的彩度基准

取五个面向儿童 / 青少年的品牌主色，实测 OKLCH C：

| 品牌 | 主色 C |
| --- | --- |
| Nintendo | 0.238 |
| Crayola | 0.231 |
| Duolingo | 0.229 |
| LEGO | 0.216 |
| Toca Boca | 0.208 |
| **均值** | **0.198** |

v0.1 的五个主题，全站最高彩度落在 **0.123–0.156**。也就是说：**这五个主题里最艳的一个颜色，比任何一个儿童品牌的平均用色还要淡一档。**

## 2. 诊断一：彩度总量不足，且分布反了

### 实测

| 指标 | v0.1 | v0.2 | 变化 |
| --- | --- | --- | --- |
| 全站最高彩度 C | 0.123 – 0.156 | 0.130 – 0.161 | — |
| **截图平均彩度 C** | **0.0141** | **0.0376** | **2.7×** |
| **C < 0.05 的像素占比** | **98%** | **78%** | −20pp |
| 90 分位 C | 0.018 | 0.064 | 3.6× |
| 99 分位 C | 0.093 | 0.160 | 1.7× |
| 单个颜色最大占屏比例 | ≈ 4%（徽章级） | ≈ 26%（色带级） | — |

注意第一行几乎没变。**v0.2 并没有把颜色调得更艳，而是把已经有的艳色从 4% 的面积放大到 26%。** 这才是"平淡"的真实病灶。

### 为什么这会让儿童不想点

三个机制，从强到弱：

1. **唤醒度（arousal）与饱和度的正相关。** 色彩心理学里比较稳的一条：饱和度升高，主观唤醒度升高（Valdez & Mehrabian 1994 的经典结果，此后大量重复）。唤醒度不是"好看"，是"愿意动"——它决定孩子是继续扫视还是切换标签页。
   低饱和 + 高明度的组合（v0.1 的 L≈0.96 的浅底）在情绪上是"安抚"，在行为上是"可以离开"。这对睡前场景是优点，对首屏是缺点。

2. **视觉显著性（visual salience）决定第一眼的落点。** 人眼的早期视觉是并行的、以对比度为驱动的。首屏里如果 98% 的像素彩度都低于 0.05，显著性图（saliency map）几乎是平的，眼睛没有落点，就会开始"漫无目的地读"，2 秒内没有钩子就离开。
   孩子比成人更依赖显著性和形状，更少依赖文字语义——**对一个还不识字或识字量小的用户，"哪里值得看"必须由颜色和形状回答，不能由标题回答。**

3. **"饱和度—游戏性"知觉。** 跨品类的观察：越是被判断为"给小孩的"产品，越倾向使用高饱和；反过来，高饱和也提高"这是玩的、不是学的"的知觉。v0.1 的配色更接近北欧家居或成人阅读类产品，会传递"这里要安静做事"的信号。
   （这一条是设计判断，不是实验结论；它的价值在于解释为什么家长第一眼会觉得"高级"，而孩子第一眼会走开。）

### 为什么不能简单地"全屏加饱和"

这是最容易走错的岔路。全屏提饱和会同时炸掉三件事：文字对比度、暗色主题的舒适度、以及"这是一个可以久坐的地方"的定位。

正确的做法是**分层**：把颜色分成"要承担文字义务的"和"纯装饰的"两类，只对后者放开彩度上限。这就是 v0.2 新增 `sky` 角色的全部理由。

```
brand      承担 4.5:1 文字义务 → 彩度被封顶
accent     承担 4.5:1 标签义务 → 彩度很高，但必须配 accentInk
sky        不承担任何文字义务 → 彩度不设上限，面积可以很大
```

## 3. 诊断二：视觉层级塌陷

### 实测与观察

| 问题 | 证据 |
| --- | --- |
| 卡片浮不起来 | `bg` 与 `surface` 的 OKLCH 明度差仅 **ΔL 0.016 – 0.058**；v0.1 里卡片只有 2px 描边，阴影只在 hover 时出现 |
| 一个颜色干三份活 | `accent` 同时是徽章底、hint 高亮、Chip 文字色 —— 每个场景都在喊，等于没人喊 |
| 首屏的主角错了 | 视觉权重最高的是右侧棋盘（黑白高对比、面积大），而不是"Puzzles that explain themselves." |
| 全站没有第二层景深 | 页面只有一个平面：底色 + 白卡片。没有天空、没有地面、没有光源 |

**为什么这一点对儿童尤其致命：** 成人靠文字层级（h1/h2/正文）建立阅读顺序，儿童靠**空间层级**——"离我近的东西更重要"。当所有卡片和背景处在同一个深度平面上，孩子得到的信息是"这些都一样，也都不重要"。

另外，纯明度差这条路在粉彩体系里走不通：要把 ΔL 拉到 0.10 以上，卡片就必须变灰，而那正是"平淡"的来源。**所以抬升感必须由别的东西提供。**

### 改法：给页面一条地平线

v0.2 把"景"写进了设计系统，用三个角色搭一个最小可用的空间：

```
sky      ── 天。铺在 body 上，从深到浅，一直延伸到第二屏
ground   ── 卡片/棋盘所在的纸面
accent   ── 光。太阳、主按钮、承诺图标、底部色带
```

具体：

- **天空画在 `body` 上，不是 hero 上。** 一个居中、有 max-width 的 section 要做全宽背景，要么用绝对定位溢出（会被 `overflow` 裁掉），要么用 `100vw`（会多出一个滚动条宽度）。画在文档上成本为零、永不出错，还顺带得到一件事：**每个路由都在同一片天空下打开，站点读起来像一个地方，而不是一堆页面。**
- **卡片改用"硬边 + 柔影"的两段式抬升**（`--pb-lift-1/2`：2px 硬偏移 + 14px 柔和投影），不再依赖明度差。硬边是玩具感，柔影是空间感，两者一起用才既"画出来的"又"浮起来的"。
- **主按钮改成 `loud` 变体**：填充 `accent`，文字 `accentInk`，带同色系的彩色投影。每屏只允许一个。
- **卡片插图加一道地平线**：上 58% 是天、下 42% 是地。一格 16:9 的图里藏了一条地干线，六张卡并排时形成节奏，而不是六块色板。
- **承诺区的四个图标变成四颗小太阳**（`accent` 实心 + `accentInk` 图标 + 硬边阴影），把明亮的颜色均匀撒在页面中段。

### 暗色主题的连带收益

Night Owl 从 `#151A2B` / `#202741` 改到 `#111522` / `#1F2433` / `#37405A`（新增 `sky`）。夜空现在是一条真实的、从深到浅的蓝渐变，黄色主按钮成为画面上唯一的高亮。**暗色主题是"彩度分层"最占便宜的场合**：亮的越亮，暗的越沉。

## 4. 诊断三：交互只有"结果"，没有"奖励"

v0.1 里三种最该被感知的时刻：

| 时刻 | v0.1 | 问题 |
| --- | --- | --- |
| 数字落进格子 | 数字模式下有 180ms 缩放；**生物模式下没有**（`CreatureGlyph` 是 svg，没挂动画） | 一半用户拿不到反馈 |
| 完成一行 / 一列 / 一宫 | 什么都没发生 | 数独里最爽的一刻被完全浪费 |
| 数字用完 | 键盘上显示 `—` | 这个设计很好，但它是静态的 |
| 切换页面 | 硬切 + 滚回顶部 | 空间感断裂 |
| 切换主题 | 只换 CSS 变量，背景有 340ms 过渡，其余瞬时 | 半硬切 |

### 为什么"反馈"对儿童不是装饰

- **因果闭合**：孩子的动作和结果之间需要一个可见的因果链。落子后格子只是"变了"，因果是弱的；落子后数字"落下来"，因果是强的。
- **完成感（competence）**：自我决定理论里内在动机的三根支柱之一。数独的天然节奏是"每 5–10 分钟有一次完成"，这个节奏必须被看见，否则孩子只记得"填了很多格"，不记得"完成了一行"。
- **不用文字表达**：目标用户里有一部分还不识字。庆祝只能用动效和颜色表达。

## 5. 浏览器新技术：用在哪、怎么用、怎么降级

这一节是"该用什么"，不是"用了什么炫技"。每一项都必须能回答：**它替代了什么手写代码，以及不支持时怎么办。**

### 5.1 View Transitions —— 页面与主题的替换

```ts
// apps/web/src/app/viewTransition.ts
export function withViewTransition(update: () => void): void {
  if (typeof document.startViewTransition !== 'function' || prefersReducedMotion()) {
    update();                                   // 降级：直接更新，没有过渡
    return;
  }
  document.startViewTransition(() => flushSync(update));
}
```

```css
/* packages/theme-core/src/tokens.css */
::view-transition-old(root) { animation: pb-fade-out 260ms var(--pb-ease-out); }
::view-transition-new(root) { animation: pb-fade-in  260ms var(--pb-ease-out); }

@media (prefers-reduced-motion: reduce) {
  ::view-transition-old(*), ::view-transition-new(*) { animation: none !important; }
}
```

要点：
- **`flushSync` 是必须的。** React 19 并发渲染，不强制同步提交的话，浏览器会在新页面还不存在时就拍快照，结果是"页面和自己交叉淡化"。
- **只用在两个地方**：路由切换、主题切换。颜色选择器的实时拖拽不包（一个拖拽会产生几十次过渡，纯属浪费）。
- 降级路径就是"直接更新"，所以不需要维护两套动画代码。

**收益**：几百行手写进出场动画 → 一个函数。**成本**：3 行 CSS + 20 行 TS。

### 5.2 `@property` —— 让一个角度可以被补间

```css
@property --pb-sun-turn {
  syntax: '<angle>';
  inherits: false;
  initial-value: 0deg;
}
@keyframes pb-sun-turn { to { --pb-sun-turn: 360deg; } }
```

首屏那颗太阳的光环是一个 `conic-gradient(from var(--pb-sun-turn), …)`。不注册 `@property`，`--pb-sun-turn` 只是个字符串，浏览器没法插值，只能一帧一帧重画；注册成 `<angle>` 之后它变成可动画的合成层属性。

**四十秒一圈**是刻意的：慢到读起来是"太阳动了"，而不是"有个东西在动个不停"。整个站点只注册这一个属性——再多的话，收益抵不过理解成本。

### 5.3 `color-mix(in oklab, …)` —— 八个颜色派生出一整套系统

这是 v0.1 就做对了、v0.2 继续放大的部分。新增的四个派生色全部来自同一组基色：

```css
--pb-sky-soft:    color-mix(in oklab, var(--pb-sky) 42%, var(--pb-surface));
--pb-sky-deep:    color-mix(in oklab, var(--pb-sky) 74%, var(--pb-brand));
--pb-accent-soft: color-mix(in oklab, var(--pb-accent) 24%, var(--pb-surface));
--pb-accent-wash: color-mix(in oklab, var(--pb-accent) 16%, transparent);
```

**为什么是 `oklab` 而不是默认的 `srgb`：** sRGB 插值会在两个高饱和色之间穿过灰点（比如蓝 → 黄会经过脏灰）。`oklab` 保持感知亮度不变，混出来的永远是"同一族"的颜色。孩子随手挑的六个颜色之所以还能拼成一个协调的站点，靠的就是这一条。

### 5.4 SVG `pathLength` + `stroke-dashoffset` —— 完成一行的扫光

数独的棋盘是 81 个 `<button>` 组成的 CSS Grid。要在一行填满时沿这一行扫一道光，最高效的做法是盖一层 9×9 viewBox 的 SVG：**一个单位 = 一个格子**，不需要任何测量。

```tsx
// games/sudoku/src/Board.tsx
<rect x={0.07} y={index + 0.07} width={8.86} height={0.86} rx={0.2} pathLength={100} />
```

```css
.pb-board__sweep rect {
  fill: none;
  stroke: var(--pb-success);
  stroke-width: 0.16;
  stroke-dasharray: 100;
  stroke-dashoffset: 100;
  animation: pb-sweep 560ms var(--pb-ease-out) forwards;
}
```

`pathLength="100"` 是关键：它把"路径长度"归一化，**一行（周长 34）、一列（34）、一宫（12）的扫光速度就完全一致**，不用为三种形状写三套时长。

配套的状态计算在 `useSudoku` 里：落子前后各算一次"哪些行列宫是满的"，取差集。**差集而非全量**——否则任何一格变化都会让已经完成的整行再闪一次，奖励变成噪音。用自增 id 做 key，撤销后重新填满同一行会重新播放。

### 5.5 落子反馈：一个动画，两个模式

v0.1 的动画挂在 `.pb-cell__digit` 上，生物模式用的是 `<CreatureGlyph>`，没有这个类，于是没有动画。v0.2 把数字和生物都包进 `.pb-cell__mark`：

```css
.pb-cell__mark { animation: pb-land var(--pb-dur-land) var(--pb-ease-out); }
@keyframes pb-land {
  0%   { transform: scale(0.55) rotate(-8deg); opacity: 0; }
  60%  { transform: scale(1.06) rotate(1deg);  opacity: 1; }
  100% { transform: scale(1)    rotate(0deg); }
}
```

只动 `transform` 和 `opacity`——这两个属性走合成器，不触发布局和重绘。81 个格子同时重排是这个规模下最容易踩的性能坑。

**填错时不用这个动画。** 错误格的反馈是一次 1.5px 的横向轻推（`pb-nudge`），读起来是"这里有点不对"，而不是"你错了"。这是有意的：这个站点不惩罚。

### 5.6 还没做但值得做的（P1/P2）

| 技术 | 用途 | 门槛 |
| --- | --- | --- |
| `view-transition-name` 逐元素命名 | 从花园里点卡片 → 棋盘"飞"进游戏页 | 需要布局连续性，棋盘尺寸在两个路由里不同，得用 `aspect-ratio` 对齐 |
| `Element.animate()` + `KeyframeEffect` | 键盘按键时数字从键位飞向格子（FLIP） | 需要读 `getBoundingClientRect`，移动端要防抖 |
| `OffscreenCanvas` + 单个 rAF 循环 | 环境层：花粉 / 萤火虫 / 飘落的叶子（≤200 粒子，预算 1.5ms/帧） | 必须有"降到 60fps 以下就自动减半粒子"的自适应，否则低端安卓会卡 |
| CSS `:has()` | 棋盘里"这个数字已经用完"的整行联动高亮 | 纯 CSS，无 JS 成本，但要在 Safari 上验一遍 |
| `content-visibility: auto` | 长页面的屏外渲染跳过 | 与 `view-transition` 快照有交互，需要实测 |

**这里的分寸：** 上面五条都是"锦上添花"。v0.1 的问题不在这里，所以它们不是 P0。一个儿童网站最怕的不是不够炫，是**动得太多**——每多一个持续动画，就多一份前庭负担，也更容易被家长判定为"又一个让人上瘾的东西"。这个站点的定位恰恰相反。

## 6. 对比度：加饱和度的许可证

做加法的同时必须守住的线。八组配色对，五个主题，全部通过：

| 主题 | 最紧的一组 | 实测 | 门槛 |
| --- | --- | --- | --- |
| Mochi Meadow | Links and focus rings | 5.17 : 1 | 4.5 |
| Sunny Kitchen | Links and focus rings | 6.14 : 1 | 4.5 |
| Lagoon Dive | Links and focus rings | 5.02 : 1 | 4.5 |
| Paper Lantern | Links and focus rings | 6.14 : 1 | 4.5 |
| Night Owl | Button label | 4.99 : 1 | 4.5 |

八组分别是：卡片正文、页面正文、**天空带上的正文**（新增）、链接与焦点环、按钮标签、**明亮色块上的标签**（新增）、错误提示、完成庆祝。

新增的两组，正是这次改动换来的自由度：

- **`sky` 上的正文**：天空带面积很大，但上面要放标题和正文，所以 `ink` 必须能在 `sky` 上读。Meadow 是 10.59:1。
- **`accent` 上的标签**：这是整个方案的关键。一个颜色**不可能**同时是 4.5:1 的文字色和一片可以放白字的亮色块——v0.1 之所以把 accent 压到 C 0.14，就是因为它在拿一个颜色干两件事。v0.2 拆成 `accent`（亮，面积大）+ `accentInk`（深，只负责标签），accent 才被允许升到 C 0.160。Meadow 的实测是 9.7:1，非常宽裕。

`accentInk` 从不交给用户选。它由 `deriveAccentInk()` 自动算：先试主题自己的 `ink`，不行退到近黑 `#141412`，再不行用纯黑或纯白——**任何 sRGB 填充色上，黑白之一必然能到 4.58:1**，所以标签永远不会读不出来。主题工作室里改"Bright"这一格时，标签色会跟着重算（实测从 9.7:1 变成 11.92:1）。

单元测试碰不到的是"接缝"，所以这一层只测接缝，跑的是**生产构建**（`vite preview`），不是 dev server——CSP、worker 分包、字体预加载只有构建后才存在：

写这一层时抓到三个真问题，都已修：

1. **键盘从角上按方向键，落到棋盘正中。** `selection` 为 `null` 时方向键从第 40 格起算，而 `selection` 只有点击才会被设——Tab 进来的人按一下「下」就跳到第 6 行。修法是格子 `onFocus` 即选中。

3. **顶栏在移动端把「For parents」缩成「Parents」**，所以按可访问名取链接的写法只在桌面成立——测试用 `/parents/i`，顺带把这件事记下来。

## 9. 取舍与风险

**1）高彩度 vs 平静。** 这个站点的差异化是"家长放心、孩子能久坐"，不是刺激。所以加的是**面积和层次**，不是整体的饱和度：正文、卡片、页面底色一动不动，全部彩度给了天空、太阳、色带和按钮。夜里孩子玩的时候，Night Owl 仍然是暗的。

**2）暗色主题的耐受度。** 暗底上高彩度更刺眼，也更容易烧屏。Night Owl 的 accent 停在 C 0.161，比白天的 0.160 并没有更高；靠的是"周围足够暗"来制造对比，不是靠"颜色更亮"。

**3）色觉障碍。** 不靠颜色承载信息是 v0.1 就定下的规矩：九只生物的身份由**轮廓特征**（耳朵、角、叶、冠）承担，灰度或红绿色盲都能分辨；棋盘状态除了底色还有边框、形状和计数。v0.2 增加的颜色全部是纯装饰，不新增任何"只能靠颜色区分"的信息。

**4）动效与可访问性。** 所有动画都走 `prefers-reduced-motion`，且降级是"直接切换"而不是"慢速播放"。没有无限循环的动画在正文区域——唯一持续运动的是首屏那颗四十秒一圈的太阳光环，它不承载任何信息。

**5）性能预算。** 全部动效只用 `transform` / `opacity` / SVG `stroke-dashoffset`。构建产物：CSS 36.4 kB（gzip 7.9 kB），首屏 JS 265.7 kB（gzip 83.9 kB，其中 React 单独 218.8 kB / 68.3 kB）。没有新增任何运行时依赖，也没有新增任何图片请求——太阳、天空、地平线全是 CSS 渐变。

**6）还没有解决的。** ΔL 依然只有 0.016–0.032，所以**卡片在纯色背景上仍然浮不起来**；v0.2 是靠"卡片坐在有色的天空上 + 硬边阴影"绕过去的，不是解决。如果将来有页面不铺天空（比如设置页），这个问题会重新出现，那时需要新的抬升手段。
